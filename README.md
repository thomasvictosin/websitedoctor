# AI Website Doctor monorepo

This repository contains two independent projects:

- [`apps/web/`](./apps/web/) — Next.js/TypeScript control panel, monitoring APIs, PostgreSQL/Prisma data layer, and central AI engine.
- [`wordpress-plugin/ai-website-doctor/`](./wordpress-plugin/ai-website-doctor/) — standalone PHP WordPress plugin with its own version, tests, and package/release workflow.

The plugin is outside the Next.js project root and is never imported, served, bundled, or executed by Next.js. The plugin and app share only the documented HTTP contract in [`contracts/wordpress-agent-api.md`](./contracts/wordpress-agent-api.md). The plugin has no Node dependencies and can be copied into a compatible WordPress installation or released independently.

## Local app development

Requirements for local development: Node.js 22.12+, Docker Compose for local PostgreSQL, and optionally Ollama. Production can use a managed PostgreSQL database and does not require Docker.

1. Copy `apps/web/.env.example` to `apps/web/.env`.
2. Run `npm run auth:hash-password --workspace apps/web`, then save the printed `ADMIN_PASSWORD_HASH` in `apps/web/.env`. Set `SESSION_SECRET` to a private random secret of at least 32 bytes.
3. Start local PostgreSQL: `docker compose up -d db`
4. Install Node dependencies from the repository root: `npm install`
5. Generate and apply the database schema: `npm run db:generate && npm run db:push`
6. Start the dashboard: `npm run dev`

The app is on [http://localhost:3000](http://localhost:3000). Run `npm run build` and `npm run typecheck` for app verification. For local AI, see [`apps/web/README.md`](./apps/web/README.md).

For managed PostgreSQL/Supabase setup, see [`docs/supabase-setup.md`](./docs/supabase-setup.md). The application remains a separate Node deployment; Docker Compose is only the local database and optional Ollama infrastructure.

Run Next.js commands through the repository-root npm scripts above; they target `apps/web`. Avoid running `next` or `npx next` from the repository root, which can create a separate root `.next` directory. If one appears, remove it with `npm run clean:root-next`; this does not remove the app's active `apps/web/.next` build.

### Claude MCP access

Claude Code and Claude Desktop can diagnose and repair sites through the app's remote MCP server at `/api/mcp`, using a personal token created under **Team → Claude MCP access**. Claude reaches the WordPress plugin only through the central app's existing approval and signed-poll workflow. See [`docs/claude-mcp.md`](./docs/claude-mcp.md).

### Compromise detection and cleanup

Every scheduled check also runs a plain-HTTP security probe that compares what visitors, Googlebot and Google-search visitors receive and inspects robots.txt and the sitemap, so cloaked SEO-spam infections are reported even when the site answers HTTP 200. Plugin 0.2.0+ adds a read-only integrity scan (core checksums, unknown PHP, malware patterns, injected .htaccess rules, recent administrators). Plugin 0.3.0+ can run a one-approval cleanup playbook from the website's **Cleanup** tab, the plugin, or the `get_cleanup_plan`/`start_cleanup` MCP tools; every change is quarantined for restore and verified from outside. Scheduled checks on serverless hosts are driven by `/api/cron/monitor` with `CRON_SECRET`. The write boundary is documented in [docs/hosting-write-safety.md](./docs/hosting-write-safety.md#wordpress-agent-compromise-cleanup-approved-7-november-2026).

### Optional Google Drive repair snapshots

For each organization, an owner or administrator can connect a dedicated Google account from a website's **Backups** tab. Enable the Google Drive API, create a Google OAuth web client, and configure `GOOGLE_DRIVE_CLIENT_ID` and `GOOGLE_DRIVE_CLIENT_SECRET` in `apps/web/.env`. Add `${APP_ORIGIN}/api/integrations/google-drive/callback` as an authorized redirect URI in Google Cloud; `APP_ORIGIN` must be the exact app origin and use HTTPS in production. Keep `SESSION_SECRET` private and at least 32 bytes: it encrypts both the stored Drive refresh token and repair snapshot content.

The app creates a Drive root folder and a separate folder for each website. Before a repair runs, the paired plugin uploads the exact operation-specific WordPress recovery point; when Drive is connected, a failed upload blocks that repair. Without a Drive connection, the plugin continues with its existing local-only recovery record, which is not uploaded later automatically. A website administrator requests restoration in the app, then a local WordPress administrator confirms it in the paired plugin. Restores cover only the saved operation target and stop if that target has changed. These are encrypted repair snapshots, **not** full-site files-and-database backups; full-site backup/restore is not implemented. Apply the updated Prisma schema with `npm run db:push` before using this integration.

## WordPress plugin development

The plugin is independently installable. Copy `wordpress-plugin/ai-website-doctor/` to `wp-content/plugins/ai-website-doctor/` and activate it. Plugin requirements, pairing, supported diagnostics, and repair limitations are in its [`readme.txt`](./wordpress-plugin/ai-website-doctor/readme.txt).

From the repository root:

- `npm run plugin:lint` — PHP syntax check.
- `npm run plugin:test` — plugin allowlist tests.
- `npm run plugin:package` — build an installable ZIP under `wordpress-plugin/ai-website-doctor/dist/`.

The plugin also has its own `composer.json` and scripts, so plugin-only development does not need the root Node workspace. Composer dependencies are currently empty; only PHP 8+ is required. Plugin checks run independently in CI, and tags named `wordpress-plugin-v<version>` create a plugin-only release ZIP.

## Repository and security

Current test commands, deliberate issue fixtures, and explicit detector coverage gaps are tracked in [`TESTING.md`](./TESTING.md).

The root `docker-compose.yml` runs only local PostgreSQL and optional Ollama infrastructure. It does not mount plugin files into the app. Keep environment secrets in `apps/web/.env` and never commit local `.env`, keys, generated output, dependencies, databases, or plugin ZIPs. Root `.gitignore` covers these files.

The local app binds to loopback by default and is intended for trusted local use. Production deployments must configure `APP_ORIGIN` as their exact HTTPS origin. Set `TRUST_PROXY=true` only behind a trusted proxy that overwrites forwarded client-IP headers. WordPress agent communication is outbound, TLS-verified, redirect-disabled, timestamped and HMAC-signed with per-installation credentials; the central service rejects stale/replayed requests and supports revocation/rotation. Repairs need both central approval and explicit local administrator action; the plugin saves a small operation-specific undo record for the exact target and prior value, not a full-site backup. It refuses an operation when a complete undo record cannot be saved.

Admin sessions use signed HttpOnly cookies and same-origin checks on state-changing web requests. Password verifiers use scrypt; login, owner API, pairing, registration, and agent requests have PostgreSQL-backed rate limits. Website ownership is scoped through organization membership. The application stores security audit events without raw client IPs or credentials. Monitoring allows only HTTP(S), pins validated public DNS results for each request, rejects unsafe redirects and private/reserved destinations, and never executes commands or gives the AI direct production access.

PostgreSQL/Prisma defines organizations/memberships, monitoring records, WordPress credentials, scans/results/evidence, issues/AI diagnoses, repair proposals/approvals/executions, backups/verification, notifications, audit logs, rate-limit buckets, durable scan jobs, and system settings. Monitoring intervals remain website configuration fields. Scan jobs use database-backed leases and retries; the due-site scheduler remains a local in-process single-instance timer. Redis is not required.

The app now supports database-backed organization accounts. The bootstrap administrator can create/remove members from the Team view; sessions identify the signed-in user and API access is scoped by organization membership. Accounts require an administrator to set a temporary password; self-service reset, invitation email, and organization switching are not configured. Plugin agent APIs remain scoped to the website associated with the authenticated installation credential.

WordPress repairs use a central allowlist and explicit approval. From either interface, **Approve & apply** can queue an eligible repair for the connected plugin; the WordPress plugin applies it on its next authenticated poll. Its WP-Cron poll is traffic-triggered, so a low-traffic site may take longer. From the plugin, **Approve & apply now** runs it immediately. Executable proposals are currently produced for plugin/theme changes isolated by a completed disposable-staging comparison, temporary deactivation of an exact active plugin mapped unambiguously to a recent PHP fatal error, exact post-link replacements, and one narrowly scoped responsive-layout repair. The layout repair is offered only when a browser scan identifies a specific element wider than its parent, the matching published page is editable, and WordPress reports `WP_ENVIRONMENT_TYPE=staging`; it adds only `max-width: 100%` to that page-scoped selector in the theme's Additional CSS. It never guesses arbitrary margins/padding and cannot execute on production. The administrator must approve it, the plugin records the exact prior CSS for guarded rollback, and the central browser rescan must clear the original overflow before the change is considered verified. Permanent redirects use their verified same-origin final destination. For a confirmed 404/410 link, the administrator supplies one replacement URL, which must be same-origin and respond successfully before a proposal is created. Both link operations target one published editable post/page and one exact old URL. The plugin stores the exact post content as an operation-specific undo record, checks that the post and old link still match, and verifies the saved edit; the central app rescans the source page and checks the selected destination, rolling the edit back if verification fails. Missing anchors, links owned by menus/templates/shortcodes, and external links remain manual guidance. The existing blog name/description setting operation now requires the exact expected current value and target value. Fatal containment is verified against fresh WordPress diagnostics and a central home-page availability check; it does not claim to repair plugin code. Connecting Google Drive adds an encrypted pre-repair snapshot for that exact operation and blocks a repair if Drive upload fails; without Drive, the plugin retains its local-only recovery record. Neither path is a full-site backup. Other findings receive evidence-specific manual remediation guidance when the system cannot name and verify an exact operation. The repair record tracks permissions, operation/risk, execution, verification, rollback, and lifecycle history. The app does not execute PHP/SQL/shell/JavaScript or arbitrary file edits.

Repair authorization is configurable per website in the Repairs view and is manual by default. The `RepairAuthorization` and `RepairPermission` records bind owner, website, individual operation, mode, risk ceiling, safety conditions, batch limit, and timestamps. Administrators can pause standing authorization; queued standing-policy work that has not been dispatched returns to pending approval. Per-website advisory locks serialize standing authorization, individual and batch approvals, permission updates, and task dispatch so conflicting repairs cannot win simultaneous checks. Every supported operation still requires an operation-specific recovery record and post-change verification, and those safety gates cannot be disabled. Standing execution creates a repair only when a fresh finding maps to one exact allowlisted operation and the paired executor checked in recently. Batch approval accepts up to 25 selected proposals, presents their change summary, rejects overlapping targets, and independently reports each queued repair. Prompt requests in the AI assistant classify diagnosis, recommendation, one issue, multiple issues, or routine maintenance against current stored evidence; the model can select only supplied issue IDs and cannot invent targets or operations. Diagnosis-only and recommendation-only prompts return information without creating proposals. Multi-issue or maintenance requests require explicit broad scope, and standing permissions are applied to prompt-created proposals only when the prompt also explicitly requests a repair. The assistant also answers permission and repair-history questions from stored app state. Explicit enable/disable instructions for automatic broken-link repairs use a deterministic parser and the existing owner-authorized permission endpoint; vague prompts do not change permissions. Explicit one-off prompt authorization is limited to low-risk exact link replacements; other operations require their displayed approval or an enabled standing permission. Unsupported or ambiguous requests remain guidance or ask for clarification. No workflow executes arbitrary code or bypasses the operation allowlist. After adding these models, apply the schema with `npm run db:push` before starting the application.

Hosting access is provider-neutral and currently has one concrete adapter: SFTP connections require a user-provided SHA256 host-key fingerprint, public DNS resolution, a configured document root, and a credential. The dashboard can inspect a bounded directory listing or file permissions; these requests verify the pinned host and root, reject symlinked path components, time out, and record an audit event. Remote hosting writes are not implemented yet, and review proposals do not change a server. SFTP is not a permanent product-level read-only requirement: once a safe writer is implemented, writing/overwriting will be optional and require explicit user confirmation that names the target, recovery point, and rollback limitations. SSH, cPanel-compatible UAPI, Plesk-compatible APIs, and other provider APIs are not implemented merely because their method names appear in the registry. A provider label does not imply a provider-specific adapter. Any write adapter must meet the requirements in [the hosting write-safety contract](./docs/hosting-write-safety.md).

## Component C: shared intelligence

The central engine is in `apps/web/lib/ai/`. It receives and organizes website/issue evidence, selects relevant evidence tools, validates structured diagnosis/proposal/instruction/review/comparison outputs, applies deterministic severity and operation-risk floors, coordinates central approval, records execution outcomes, compares before/after evidence, and can request a separately confirmed WordPress rollback. The WordPress plugin does not run an AI model and has no import/dependency on the web app. It is only an evidence collector, user interface, and allowlisted local executor using the documented HTTP contract.

Available evidence tools include the central DNS-pinned HTTP availability probe, a bounded Playwright same-origin crawl with sitemap discovery, axe-core automated accessibility rules, responsive/browser observations and timing metrics, and WordPress configuration/plugin/WP-Cron/authorized-log evidence supplied by the plugin. This is not exhaustive crawling or full WCAG certification. If Ollama is offline, central issues and deterministic severity still persist; AI analysis/review is explicitly marked unavailable and cannot execute repairs. If WordPress is offline, independent HTTP/browser monitoring can report site evidence, but the central app cannot execute WordPress repairs without a reachable, explicitly paired agent.
